**so that** I can move freely through a ten-hour audiobook instead of tapping a skip button dozens of times.

<testing_posture>
Neither task in this plan is marked `tdd="true"`, and that is a deliberate, defensible call rather than an omission:

- This repo's only test harness is `pnpm test:logic` → `node --test scripts/library-logic.test.mjs`, which imports DOM-free `lib/*.ts` modules under Node's built-in type stripping. No React test renderer, no jsdom, and no browser-driver is installed, so a drag lifecycle built on pointer capture has nothing in this repo that can execute it.
- The one piece of this plan's logic that *is* mechanically testable — bounding the committed seek value — is `clampSeek`, which 03-02 already covers with exact-value `node --test` cases at both inclusive bounds. Re-deriving a second bounds function here purely to have something to test would create the duplication this plan exists to avoid.
- The drag lifecycle's real failure modes (does the commit callback fire on iOS touch release; does the resume call survive iOS's gesture-unlock rule) are device-behavior questions that a unit test could not answer even if a renderer existed. They are carried as named `<human-check>` blocks with a pre-approved fallback, which is the honest instrument for them.

Introducing a React testing stack is out of scope for this phase and is not smuggled in here.
</testing_posture>
